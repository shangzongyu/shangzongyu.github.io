# 博客写作与发布

从仓库根目录运行命令。先确定目标文章和用户要求做到哪一步。写稿、上传图片、提交和推送可以独立执行。明确要求完整发布到 GitHub 时，按下述顺序完成。

## 写草稿

- 新建文章用 `mise run blog:new "文章标题" -c 工具推荐 --no-open`。按实际内容选分类。有现成草稿时直接续写原文件。
- 草稿保存在 `content/posts/`，保留 `draft: true`。配图放在文章旁的同名 `.assets/` 目录，通过相对路径引用，方便在不同编辑器中继续写。
- 如果用户只要求写稿或编辑，到草稿完成为止。

## 上传配图

- 用户明确要求上传配图或完整发布时，执行 `mise run blog:image 2026-工具推荐_T3-Code.md`，参数换成目标文章的文件名或路径。
- 命令用 `upgit` 将正文和封面引用的本地图片传到 `shangzongyu/blog-image`，全部成功后统一替换链接。检查改写结果，确认准备发布的图片已换成公开 URL。上传失败时报告具体原因，并在修复后重试；同一张图片使用同一远端路径。
- 如果只授权上传配图，完成链接替换后交还稿件。GitHub 令牌配置和支持的引用格式见[脚本工具说明](../../../scripts/README.md)。

## 提交与推送

1. 明确要求发布文章时，将目标文章的 `draft` 改为 `false`，确认分类和配图链接。仅要求准备发布时，到本地检查为止；提交和推送按用户已经授权的范围执行。
2. 提交前运行 `mise run lint`。在本次文章范围内修复 zhlint 报告的问题。检查目标文章的变化，暂存并提交该文章；若其他文件的格式问题阻塞提交，列出对应文件。
3. 推送前检查当前分支、远端和待推送提交。正式发布目标是 `origin/master`。分支分叉时先检查两边提交；若推送会带上未经授权的提交或需要覆盖远端历史，停下来说明具体情况。
4. 推送 `master` 后由 GitHub Actions 部署到 `gh-pages`。用户要求确认上线时，再核对对应提交的部署状态。记录已完成的步骤和仍待处理的事项。[部署流程](../../../.github/workflows/deploy.yml)
